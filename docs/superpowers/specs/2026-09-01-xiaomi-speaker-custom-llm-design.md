# 设计文档：小爱音箱接入自订阅大模型的家庭智能体

- **日期**：2026-09-01
- **状态**：已确认（用户于 2026-09-01 批准）
- **路径**：方案 A——MiGPT 式"接管"小爱音箱，复用其唤醒/ASR/TTS，大脑替换为自订阅 LLM

## 1. 背景与目标

家庭智能家居以小米产品为主，设备连接小米网关，通过小爱音箱语音控制。小爱音箱已接入官方大模型，但用户希望将"大脑"换成自己订阅的大模型（有 API Key，支持 Function Calling）。

**目标**：

- 语音体验无感切换：继续用"小爱同学"唤醒，语音进语音出
- 自然语言智能体：理解模糊意图（"我要睡了"、"有点冷"），由 LLM 自主决策组合控制设备
- 架构解耦：小米接入层与 LLM 智能体层分离，未来可平滑迁移到 Home Assistant 等中枢

**非目标**：

- 刷机或替换音箱硬件（小爱音箱固件闭源，不可行）
- 多入口（App/微信/文字）交互——本期纯语音
- 自建 ASR/TTS——完全复用小爱能力

## 2. 关键决策记录

| 决策 | 结论 | 理由 |
|---|---|---|
| 技术路线 | 接管式（轮询小爱对话 + 掐断原生应答） | 音箱固件闭源无法刷机；mi-gpt 等开源项目已验证链路可行 |
| 底层接入代码 | **vendor 策略**：将 mi-gpt（已于 2026-04 归档）的接入层代码复制进本仓库 adapter 模块自行维护，不作为外部依赖 | 归档项目无人维护；xiaogpt（活跃）但不支持米家设备控制；vendor 后协议变更可自主修复 |
| 触发策略 | 口令模式起步（如"请……"开头才进 LLM），全接管作为实验性开关 | 全接管会让"开灯"类原生秒回指令也走轮询+LLM，体验变差且费 token |
| 播报通道 | 双通道：默认小爱原生 TTS（零依赖）；预留第三方 TTS（合成音频文件 + 本地 HTTP 服务供音箱拉取）作为换音色扩展点 | 原生 TTS 音色固定但零依赖；第三方 TTS 需音频 URL 音箱可达 |
| 设备控制 | 直连小米云 MIoT 接口 | 无需引入 Home Assistant，起步复杂度最低 |
| 抽象边界 | 智能体层只见 `IRemoteDevice` 接口 | 换 HA/Matter 时只换接入层，智能体层不动 |
| 运行环境 | 家中常开设备（Docker Compose 或裸 Node.js） | 7×24 常驻，内网直连，低延迟 |
| AI 入口音箱 | 指定小爱音箱 Art（L09A）；mini（LX01）保持原生 | 两台均为独立 did 互不干扰；Art 音质更好；均可被设备控制层调用 |

### 2.1 目标硬件兼容性（依据 mi-gpt 官方兼容列表）

| 音箱 | 型号 | TTS 播报 | 唤醒 | 限制 |
|---|---|---|---|---|
| 小爱音箱 Art（AI 入口） | L09A | ✅ 指令 `[3,1]` | ✅ 指令 `[3,2]` | 不支持连续对话（须关闭流式响应）；**无法查询播放状态** |
| 小爱音箱 mini | LX01 | ✅ 指令 `[5,1]` | ✅ 指令 `[5,2]` | 同上 |

设计约束：两台机型均查不到播放状态，因此**不依赖播放状态回读**——打断与播报确认一律采用"盲发"策略（见第 6 节）；流式响应不可用（本设计未依赖）。

## 3. 总体架构

```
┌─────────────┐   轮询/指令/播报    ┌──────────────────┐
│  小爱音箱     │ ◄──────────────► │  小米接入层 (Adapter) │
│ (唤醒+ASR+TTS)│                  │  mi-gpt 协议封装     │
└─────────────┘                  └────────┬─────────┘
                                          │ IRemoteDevice
                                          ▼
                                 ┌──────────────────┐      ┌─────────┐
                                 │  LLM 智能体层 (Agent) │ ◄──► │ 用户订阅  │
                                 │  Function Calling   │      │  LLM API │
                                 └──────────────────┘      └─────────┘
```

三个模块跑在常开设备上。

## 4. 模块设计

### 4.1 小米接入层（adapter）

- **职责**：登录小米云、轮询小爱新对话、掐断原生应答、调 MIoT 接口控制设备、TTS 播报
- **实现**：vendor mi-gpt 的接入层代码（登录 / MiNA / MIoT 协议封装）进本模块，作为自有代码维护
- **登录**：支持小米账号密码登录，同时支持 cookie / token 文件方式（规避异地登录风控）
- **对外接口**：实现 `IRemoteDevice`：
  - `listDevices(): Promise<DeviceInfo[]>`
  - `getDeviceState(deviceId): Promise<DeviceState>`
  - `executeAction(deviceId, action, params): Promise<ActionResult>`
- **轮询频率**：约 1 秒/次
- **触发词**：默认口令模式（可配置关键词列表，如"请……"开头），全接管为实验性配置项

### 4.2 LLM 智能体层（agent）

- **职责**：维护对话历史与设备快照，组装 system prompt，调用 LLM，解析 tool calls 并回环执行
- **工具定义**（Function Calling）：
  - `list_devices()` — 列出家中设备及状态
  - `control_device(device, action, params)` — 控制设备
  - `get_device_state(device)` — 查询设备实时状态
- **Prompt 策略**：设备以人类可读名称（"客厅主灯"）注入而非 device id；附带设备能力描述（可调亮度/色温等），利于 LLM 理解
- **响应模式**：非流式（目标机型不支持流式播报；流式为将来换机型时的可选项）

### 4.3 设备缓存

- 定期（如 30 秒）拉取米家设备列表 + 状态，生成设备能力描述快照供智能体层使用
- 控制指令执行后立即刷新该设备状态

## 5. 核心数据流（"我要睡了"）

1. 用户对音箱说"请，我要睡了"（口令触发）→ 小爱 ASR 转文本
2. 接入层轮询发现新对话且命中触发词 → 立即下发"停止当前回答"+ 播放占位音频压制原生应答（防小爱插嘴；因目标机型查不到播放状态，采用盲发策略，不回读确认）
3. 文本进入智能体层 → 携带设备快照 + 对话历史调用 LLM
4. LLM 返回 tool calls：`control_device(客厅主灯, off)`、`control_device(空调, off)`
5. 智能体层执行工具 → 结果回传 LLM → LLM 生成最终回复"晚安，灯和空调都关了"
6. 接入层通过小爱 TTS 通道推送到音箱播报

## 6. 异常处理

| 场景 | 处理 |
|---|---|
| LLM 超时/报错 | 播报兜底话术"我脑子转不动了，稍后再试" |
| 控制指令失败 | 播报具体哪台设备未成功 |
| 小爱原生应答抢先 | 盲发停止指令 + 占位音频压制（目标机型查不到播放状态，不回读确认；接受偶尔漏半句） |
| 小米登录态失效 | 播报"需要重新登录" + 推送通知到手机（登录态可维持数周；支持 cookie/token 文件重新导入） |
| LLM 幻觉调用不存在的设备 | 工具层校验设备名，不匹配时回喂可用设备列表让 LLM 自纠（一次重试） |
| 多轮对话并发 | 对话队列串行处理，防止并发控制冲突 |

## 7. 测试策略

- **接入层**：mock 小米云接口的单元测试
- **智能体层**：预设对话用例测意图→工具调用映射（如"我要睡了"→关灯关空调），不真控设备
- **端到端**：先接一台不重要的灯（台灯）实测语音全链路，验证后再放开全部设备

## 9. 已知风险与限制

- 轮询机制固有 1~2 秒延迟
- 依赖小米云非官方接口，登录态偶发失效；mi-gpt 上游已归档，**协议变更时需自行修复 vendor 进来的接入层代码**（隔离在 adapter 内，影响面可控）
- 目标机型（L09A/LX01）不支持连续对话与播放状态查询：打断与播报确认只能盲发，小爱原生应答偶尔"漏"出半句
- 账号风险：小米可能对异常调用风控（参考 mi-gpt 免责声明，自用低频调用风险较低）
